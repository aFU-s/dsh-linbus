# 降本增效路线（按 ROI 排序）

依据：[token 消耗分布](token-consumption.md)（444 步、509 次工具调用、55 张图、118.6M 累计输入）。
核心事实：**88% 花在“每一步重发历史”**，截图只占 10.3%。

## 一句话结论

先做两件“免费”的事——**新会话/专用模式** + **farm 取代逐步视觉**；
再考虑截断工具结果、降 reasoning；截图优化放最后。

## 收益 / 成本矩阵

| 优先级 | 动作 | 现状 | 目标 | 预计节省 | 实施成本 |
|---|---|---|---|---|---|
| **P0** | 每次任务用新会话（巴士模式） | 平均 267k token/步 | 20k–50k/步 | 输入降 **5–10×** | 0，习惯改变 |
| **P0** | `limbus_farm` 取代逐步截图 | 40–50 步/场 | 1–3 步/场 | 步数降 **15–40×** | 已建，需修启动 |
| **P1** | 工具结果截断/摘要 | 占 44.1% | 压 30–50% | 总 token 降 **13–22%** | 低（配置/习惯） |
| **P1** | reasoning 降档（medium/low） | 助手历史占 44.1% | 降 10–20% | 总 token 降 **4–9%** | 低（需 profile/会话设置） |
| **P2** | 截图裁剪/缩放 | 占 10.3% | 减半 | 总 token 降 **5%** | 中（改插件） |
| **P2** | 工具 schema/系统提示精简 | 占 1.5% | 1% | <1% | 低，但不值得 |

> 两件 P0 乘起来：一场从“几十步 × 几十万上下文”变成“1–3 步 × 几万”，
> 理论上 30–100×；保守按 **10–30×** 估算。

## 怎么落地

### P0-1：新会话 / 巴士模式

- 重启 DSH → 新建会话选「边狱巴士」；
- 每个任务一个会话，跑完就结束；不要在开发会话里顺手刷本；
- 模式只挂 `limbus_*` + `read_image/write` + `pwsh` + skill，系统提示更短。

### P0-2：farm 优先

- 能 `limbus_farm_start` 就不要“截图→点→截图”；
- farm 启动仍不稳时，用 `tool-pwsh` 后台 fallback 一次（技能里写了命令），
  不要退回逐步手动；
- 只有 `failed/partial` 才看截图，且只看一张。

### P1-1：工具结果截断

- 长文件读取、grep、日志、报告不要整段留在历史里；
- 巴士模式已挂 `tool-result-pruner`（8192 字符）和 `/compact`；
- 开发会话里也多用摘要，少贴全文。

### P1-2：reasoning 降档

- 当前 profile 是 `reasoningEffort: high`；游戏任务用 `medium` 就够；
- 模式本身不能改 host 的模型/推理；要么在会话里选，要么做一个独立
  `limbus` profile（`reasoningEffort: medium`）。

### P2：截图优化

- 只在失败时看；看的时候裁到关键区域（底部栏/对话框），别整张 1920×1080；
- 一张全屏图约 1024 token；裁剪后可能只占 1/10。

## 目标成本

以一场经验本 10、7 回合为例：

| 方式 | 模型往返 | 估算 token | 估算费用 |
|---|---:|---:|---:|
| 逐步视觉（本次手动） | 40–50 | ~12M | ~¥0.45 |
| 旧的长会话战斗 | 50+ | ~59M | ~¥1.45 |
| 新会话 + farm | 1–3 | 0.1–0.5M | **~¥0.02–0.05** |

每天 3 场：从 ¥1.4–4.4 降到 **¥0.06–0.15**。

## 复现与度量

每次跑完，用同一套脚本量一下这次会话：

```powershell
node docs/collect-token-context.mjs <session.v4.jsonl.zstd> docs/token-context.json
```

目标：**单场 < 0.5M 累计输入 token**；超过就说明又在“逐步截图”了。
